# Единый диалог авторизации — дизайн прототипа

## Цель

Заменить самостоятельные экраны входа и восстановления единым адаптивным диалогом, который открывается поверх текущей страницы и сохраняет контекст пользователя, включая checkout. Прототип демонстрирует ветвление сценариев без реальных SMS, backend и хранения паролей.

## Архитектура

Глобальный `AuthProvider` размещается в дереве приложения рядом с остальными провайдерами. Он открывает `AuthDialog` из шапки, мобильной навигации, личного кабинета и checkout, хранит только состояние открытого окна и сообщение об успешном завершении. Прямые маршруты `/profile/auth` и `/profile/recovery` становятся маршрутами-мостами: открывают нужный сценарий и заменяют фон на главную.

`AuthDialog` владеет локальной машиной состояний и несекретными полями текущей сессии окна. Пароли существуют только в React state, очищаются при смене секретного шага и закрытии, не попадают в `localStorage`, URL, логи или общий контекст.

## Сценарии

- Вкладки «Вход» и «Регистрация» всегда доступны на первом уровне.
- Вход: «По SMS» проходит телефон → SMS-код → успешное закрытие; «По паролю» принимает телефон и пароль, содержит «Забыли пароль?» и завершает вход без сохранения пароля.
- «Забыли пароль?» предлагает два разных действия: перейти к обычному входу по SMS или восстановить пароль через телефон → SMS-код → новый пароль с повтором → успешное закрытие.
- Регистрация принимает имя, телефон, обязательное согласие на обработку данных и условия сервиса; рекламная подписка отдельная и необязательная.
- После SMS новый пользователь может установить пароль или продолжить без него. Демонстрационный существующий номер `+7 900 000-00-00` предлагает вход вместо повторной регистрации.
- Флаг «Для компании» добавляет после SMS шаг подключения организации по ИНН. ИНН `7600000028` демонстрационно находит ООО «Гараж Профи»; реального запроса нет.
- «Нет доступа к телефону» закрывает диалог и переводит в `/profile/help`.
- Назад сохраняет имя, телефон, тип регистрации и согласия; секретные поля не обязаны сохраняться.

## Демонстрационные состояния и backend

Код `1234` успешен, `0000` истёк, другие значения ошибочны. Повторная отправка становится доступна после таймера; истёкший код снимает ожидание. Пароль в прототипе валидируется локально только для демонстрации интерфейса.

Рабочей системе потребуется backend для безопасного хеширования и хранения паролей, политики сложности, ограничения попыток, управления сессиями, одноразовых и ограниченных по времени SMS-кодов, восстановления, аудита, защиты от перебора и интеграции с SMS-провайдером. Прототип не является моделью информационной безопасности.

## Доступность и адаптив

Диалог имеет `role="dialog"`, `aria-modal`, управляемый начальный фокус, focus trap, закрытие по Escape и возврат фокуса вызвавшему элементу. На mobile окно занимает безопасную высоту, прокручивает только содержимое, а основные действия не перекрываются нижней навигацией. Учитывается `prefers-reduced-motion`.

## Проверка

Unit/integration-тесты покрывают оба входа, регистрацию физлица и компании, существующий телефон, обе ветки восстановления, ошибки/истечение/повтор SMS, возврат назад и отсутствие записи пароля. E2E проверяет entry points из шапки, ЛК и checkout, сохранение URL после успеха, прямые auth-маршруты и desktop/mobile.
