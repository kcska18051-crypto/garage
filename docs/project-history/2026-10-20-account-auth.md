# Согласованность авторизации личного кабинета

Согласованная пользователем задача выполнена после публикации пакета избранного/корзины `c30ea18`; база `f8c1d2f`. Меню каталога не входит в задачу.

## Причина и решение

- `AuthState` уже управлял шапкой, но `ProfileShell` всегда показывал данные `ProfileProvider` и все личные страницы. Поэтому гость видел демопользователя и одновременно «Войти / регистрация».
- Источник состояния теперь один — `AuthState.isAuthenticated`. У гостя нейтральная карточка «Гость», «Войти / зарегистрироваться» и экран входа на прямых URL личных данных/заказов/документов/адресов. Персональная форма и подтверждённый телефон не выводятся. Избранное, просмотренные товары и справка остаются доступны гостю без ФИО и карточки авторизованного пользователя.
- Существующие SMS/регистрация/восстановление и явно обозначенный демо-вход по паролю сохранены. Вход не выполняется автоматически ради замены кнопки. После явного завершения сценария сохраняется marker демосессии в `sessionStorage`; он переживает reload в той же вкладке. Это не серверный токен и не production-защита; реальная авторизация/контроль доступа требуют backend-интеграции. Пароль/код/телефон в marker не сохраняются.
- Вошедший видит данные с пометкой «Демо-профиль» и «Выйти». Выход удаляет marker, меняет шапку/sidebar/личный экран на гостевой. Он не вызывает удаление/сброс профиля и не очищает корзину/избранное.
- Избранное сохраняется отдельно в `garage-favorites-v1`: демоначальное заполнение перенесено из эффекта ProfileProvider в начальное состояние CommerceProvider, чтобы повторный mount не возвращал удалённые товары. Logout не пересоздаёт эти провайдеры.

## Checkout и сохранение намерения

- Гостю не показываются подтверждённый телефон, профильные организации или сохранённые адреса как будто он уже вошёл. Данные текущего заказа и выбор способа получения остаются на месте.
- Вход из checkout возвращает на тот же pathname/query/hash. После завершения данные профиля доступны, а выбранные пункт/оплата/комментарий не сбрасываются.
- Оформление не выдаёт гостю ложный успешный заказ с демополучателем: действие до входа открывает auth-сценарий; после входа используется существующая валидация. Сценарий незарегистрированного заказа не добавлялся.

## Проверки

- TDD сначала воспроизвёл раскрытие ФИО гостю и отсутствие согласованного guest/account состояния.
- Релевантный прогон существующих auth/profile/checkout проверок: 59/59; финальные AuthSession: 4/4 (включают две дополнительные проверки). Тесты авторизованных разделов используют явно названную fixture демосессии, гостевые и auth-flow тесты не обходят вход.
- Новый E2E: 4/4 на 360/390/1440/1920. Гость → явный демо-вход → прямой URL/reload → выход → reload; отсутствие личных данных у гостя, согласованность действий, сохранение корзины и изменённого избранного. Вход из checkout сохраняет точный URL с query/hash, пункт, СБП, комментарий и доступность оформления после входа.
- Регрессия самовывоза: 4/4 на тех же ширинах, теперь с явным демо-входом. Existing E2E для приватных разделов обновлены, чтобы начинать с явного входа, а не подразумевать авторизацию гостя. Механика удаления/восстановления профиля не менялась.
- Скриншоты гостя/mobile и вошедшего/desktop осмотрены, document overflow не обнаружен. `build:pages` успешен, предупреждение об общем JS chunk >500KB — отдельная оптимизация.
